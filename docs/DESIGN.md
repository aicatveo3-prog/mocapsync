# MocapSync 설계 (확정)

이 문서는 **이미 검토를 마친 결정 사항**입니다. 구현 중에 재조사·재논의하지 않습니다.
바꿔야 할 근거가 새로 생기면 이 문서를 고치고, 왜 바꿨는지 함께 적습니다.

---

## 1. 목표

마스터 폰에서 촬영 버튼을 누르면 다른 폰들도 동시에 녹화되고, 촬영이 끝나면 PC로 자동
업로드되어 3D 모션이 복원되고, 브라우저에서 결과를 확인할 수 있는 시스템.

3D 복원은 직접 만들지 않고 **Pose2Sim 에 위임**합니다.
우리가 만드는 것은 **촬영 오케스트레이션 + 데이터 정렬 + 뷰어**입니다.

---

## 2. 확정된 기술 스택

| 항목 | 결정 | 근거 |
| --- | --- | --- |
| 3D 파이프라인 | **Pose2Sim** (`uv pip install pose2sim`) | BSD-3-Clause, 무료 + 상업 이용 가능, 논문 검증 관절각 오차 2~6° |
| 2D 모델 | **RTMPose `Body_with_feet` (HALPE_26)**, `mode='performance'` | `Whole_body`(133점)는 몸 정확도가 더 낮음 (공식 문서 명시) |
| 캘리브레이션 | ~~`extrinsics_method='scene'`~~ → **자체 도구** (`tools/calibrate.py`, §4.5) | 2026-09-28 변경: 우리 카메라는 동기돼 있으므로(사이드카 시각) 판을 들고 돌아다니는 동시 촬영으로 스테레오를 풉니다. 'scene' 은 사람이 점을 클릭해야 하고 줄자 측정 오차가 그대로 들어갑니다 |
| 필터 | Butterworth | 걷기 3~6Hz, 달리기 6~15Hz |

## 3. 안드로이드 앱 설계

### 3.1 플랫폼

- **Kotlin + Jetpack Compose**, 단일 APK 에서 MASTER / SLAVE 역할 선택
- Flutter / React Native 는 **불가**. 저수준 프레임 타임스탬프 제어가 필요해서 네이티브 필수.

### 3.2 기기 탐색 / 네트워크

- Android NSD (mDNS), 서비스 타입 `_mocapsync._tcp` → **IP 입력 불필요**
- 마스터 폰 핫스팟 우선(야외 대응), 공유기도 지원
- Foreground Service + wake lock

### 3.3 클럭 동기

자체 SNTP. `SystemClock.elapsedRealtimeNanos()` 사용.

```
20~50회 왕복 후 RTT 가 최소인 샘플만 채택
offset = ((t2 - t1) + (t3 - t4)) / 2
```

목표: **오차 2ms 미만**

### 3.4 녹화 시작 — "예약 시작" ★핵심

마스터가 `(현재 + 500ms)` 시점을 지정해 브로드캐스트하고, 슬레이브가 자기 클럭으로
변환해서 그 순간에 시작합니다.

- 이렇게 하면 WiFi 패킷 지연이 무해해집니다.
- **"지금 찍어" 방식은 절대 쓰지 않습니다.**

### 3.5 프레임 타임스탬프

`CameraX` + `Camera2Interop.setSessionCaptureCallback` 으로 `CaptureResult.SENSOR_TIMESTAMP`
를 프레임마다 기록합니다.

- `SENSOR_INFO_TIMESTAMP_SOURCE` 가 `REALTIME` 이면 그대로 사용
- `UNKNOWN` 이면 `(elapsedRealtimeNanos - uptimeNanos)` 델타로 변환
- **기기마다 다르므로 "기기 진단" 화면에서 실측할 것. 추측 금지.**

> 주의: 이 델타는 기기가 절전에 들어갈 때마다 커집니다. 상수로 캐시하면 안 되고
> 녹화 세션마다 다시 재야 합니다.

### 3.6 사이드카 JSON

```json
{
  "device_id": "...",
  "clock_offset_ns": 0,
  "timestamp_source": "REALTIME | UNKNOWN",
  "target_fps": 60,
  "frames": [[0, 123456789], [1, 140123456]]
}
```

### 3.7 카메라 강제 설정

- AE / AF / AWB **LOCK**
- 손떨림보정 **OIS / EIS OFF**
  → OIS 가 켜져 있으면 내부 파라미터가 프레임마다 변해 캘리브레이션이 무의미해집니다.
- 60fps 이상
- 셔터 1/500 이상

### 3.8 ★1일차부터 반드시

**"로그 내보내기" 버튼.**
개발자가 실기기 테스트를 할 수 없으므로, 사용자가 로그를 붙여줄 수 있어야 디버깅이 됩니다.

## 3.9 실측으로 확인된 환경 제약 (2026-09-17)

이 프로젝트에서 두 번 물린 함정입니다. 둘 다 같은 뿌리(**경로에 한글이 있으면 C++ 툴체인이 깨진다**)입니다.

| 대상 | 증상 | 우회 |
| --- | --- | --- |
| **Android Gradle Plugin** | `Your project path contains non-ASCII characters` 로 빌드 거부 | ASCII 경로 디렉터리 정션(`mklink /J`)에서 빌드. **정션이 통합니다.** CI(리눅스)는 무관 |
| **OpenSim 4.6 (C++ 코어)** | `Cannot open file ..._scaling_setup.xml` (파일은 실제로 존재함). `Pose2Sim.kinematics()` 에서만 터짐 | **정션으로 우회 안 됩니다** — Pose2Sim 이 경로를 `resolve()` 해서 원래 경로로 되돌립니다. 작업 폴더 자체를 ASCII 경로로 둬야 합니다 |

검증 방법: 동일 프로젝트를 ASCII 경로로 복사해 `kinematics` 만 재실행 → `.mot` / `.osim` 정상 생성.

### 4단계 설계에 주는 결론

PC 파이프라인은 **세션 작업 폴더를 항상 ASCII 경로에 만들어야 합니다.**
코드는 리포에, 데이터는 ASCII 경로에 두는 분리 구조로 갑니다.
`tools/pose2sim_demo.py` 는 리포 경로가 non-ASCII 면 작업 폴더를
`~/Pose2SimWork` 로 자동 이동시키고, 실행 전에 경로를 점검해 조기 중단합니다.

## 3.10 아이폰 11 실측 결과 (2026-09-24)

실기기(iPhone12,1 / iOS 17.5.1)에서 진단 앱으로 측정한 값입니다. 추측이 아닙니다.

### ★ 시계 도메인 — 프로젝트의 전제 확인됨

```
CLOCK_UPTIME_RAW        = 520885686916 ns   (동기/사이드카에 사용)
CMClockGetHostTimeClock = 520885686333 ns   (프레임 타임스탬프 기준)
차이                    = -583 ns
```

**583 ns.** 두 값을 읽는 사이의 명령어 실행 시간 수준입니다. 사실상 같은 카운터입니다.

| | 값 |
| --- | --- |
| 동기 목표 | 2,000,000 ns |
| 시계 변환 오차 | **583 ns** |
| 오차 예산 대비 | **0.03%** |

→ **프레임 타임스탬프를 우리 시계로 옮기는 비용이 0입니다.** 규약 §1 의 규칙이
실기기에서 만족됩니다. 안드로이드의 REALTIME/UNKNOWN 분기가 불필요해졌습니다.

미검증: `누적 절전시간` 지표는 폰이 부팅 8.7분 뒤라 0 이었습니다.
절전을 거친 뒤 재측정해야 검증됩니다.

### 카메라 선택

> **2026-09-27 변경: 주 카메라 = 후면 초광각 `builtInUltraWideCamera` (기본 카메라 앱의 0.5x).**
> 사용자 결정, 광각과 비교 촬영 없이 바로 기본값으로 바꿈. 이유: 좁은 방에서 전신이
> 들어옴(첫 광각 촬영에서 머리가 잘림), OIS 없음, 고정초점(캘리브레이션 때와 촬영 때
> 초점이 같음이 물리적으로 보장). 대가: 같은 거리에서 사람이 약 51% 크기
> (tan 34.85° / tan 53.9°), f/2.4 라 빛이 약 1.8배 필요(실내 ISO 가 이미 상한 근처였음),
> 가장자리 왜곡이 큼 → 러너가 `triangulation.undistort_points = true` 로 돌립니다.
> 초광각이 없는 기기만 광각으로 물러나고 경고합니다. 세션에 렌즈가 섞이면
> `lens_mismatch` 경고. 아래 표와 근거는 변경 전 판단 기록입니다.

(변경 전) **주 카메라 = 후면 광각 `builtInWideAngleCamera`, 1920x1080 @60fps, 화각 69.7도**

| 카메라 | 1080p60 | 셔터지정 | 초점 | OIS | 화각 | 판정 |
| --- | --- | --- | --- | --- | --- | --- |
| **후면 광각** | 8포맷 | ✅ 1/71,428초 | AF 잠금 가능 | ⚠️ 탑재 | 69.7° | **채택** |
| 후면 초광각 | 8포맷 | ✅ | **고정초점** | **없음** | 107.8° | 예비 |
| 전면 | 6포맷 | ✅ | 고정초점 | 탑재 | 73.3° | 미사용 |
| 후면 Dual Wide | 4포맷 | ❌ | 잠금 가능 | 불명 | 107.8° | **사용 금지** |

채택 근거: 피험자에 할당되는 픽셀 수. 카메라가 2대뿐이라 각 시점의 품질이 중요합니다.
초광각은 캘리브레이션이 더 안정적이지만 107.8도에서 사람이 작게 찍혀 2D 검출
정밀도가 떨어집니다.

### 실측으로 바로잡은 판정 오류 2건

**① 고정초점을 `[불가]` 로 잘못 판정했었음**

아이폰 11 의 초광각·전면은 **자동초점 기구가 없는 고정초점**입니다
(초광각 AF 는 13 Pro, 전면 AF 는 14 부터). 그래서
`isFocusModeSupported(.locked)` 가 false 를 돌려줍니다 — 잠글 기구가 없어서입니다.

고정초점은 초점거리가 **물리적으로** 변할 수 없으므로 캘리브레이션 안정성이
'잠글 수 있는 AF'보다 **오히려 낫습니다.** 판정을 세 갈래(고정초점 / 잠금가능 /
잠금불가)로 바꿨습니다.

구분법: 어떤 초점 모드도 지원하지 않으면 초점 기구가 없는 것입니다.

**② 합성 카메라를 걸러내지 않았음**

`builtInDualWideCamera` / `DualCamera` / `TripleCamera` 는 물리 렌즈가 아니라
여러 렌즈를 **자동 전환**하는 가상 장치입니다. 촬영 중 렌즈가 바뀌면
초점거리·화각·왜곡이 통째로 바뀝니다. **OIS 보다 심각합니다.**
진단에 "사용 금지" 항목을 최상단에 추가했습니다.

### 고프레임의 숨은 대가 — 화각 크롭

| 포맷 | 화각 | 비고 |
| --- | --- | --- |
| 1080p **60**fps | **69.7°** | 정상 |
| 1080p **120**fps | **38.4°** | ★ 크롭. 피험자가 프레임을 벗어남 |
| 1080p **240**fps | 69.7° | binned (화질 저하) |

고프레임이 공짜가 아닙니다. **1080p60 으로 갑니다.** 240fps 는 빠른 동작
실험용으로 보류합니다.

### OIS 미해결 — 측정으로 판정할 것

후면 광각에 OIS 가 있고 **끄는 공개 API 가 없습니다**(Apple 개발자 포럼에 질문이
올라와 있는 미해결 사안). 완화책:

1. 삼각대 고정 → 보정할 흔들림이 없으면 렌즈가 기준 위치에 머묾
2. **측정으로 판정**: 고정 삼각대로 장면을 수십 초 촬영해 재투영 오차가 시간에
   따라 배회하는지 확인
3. 배회하면 초광각으로 전환 (OIS 없음 + 고정초점)

## 3.11 클럭 동기 1차 실측 (2026-09-24, 아이폰 11 ↔ PC 마스터, WiFi)

### 측정값

```
왕복 40회 / 0.96초 / 간격 5ms / 워밍업 없음
오프셋   +5,522,184.805 ms
최소 RTT      4.810 ms
오차 상한     2.405 ms   (= 최소RTT / 2)
실측 흔들림   1.240 ms
판정: 미달 — 상한 2.405 ms >= 목표 2.0 ms
```

### 해석

**오프셋 +5,522초(약 92분)는 정상입니다.** 두 기기의 부팅 기준 단조시계를
비교한 값이라 부팅 시각 차이만큼 벌어지는 것이 당연합니다. 이 값의 크기는
정확도와 무관합니다.

**실패한 것은 최소 RTT 하나입니다.** 4.810 ms → 4.0 ms 미만으로 내려가야
목표(오차 상한 2 ms)가 증명됩니다. 필요한 개선폭 약 17%.

### 상한 2.405 ms 의 의미 — 최악값이지 실측 오차가 아님

규약 §4.3 에서 추정 오차는 정확히 `(d_up − d_dn) / 2` 입니다.
경로가 대칭이면 **0** 입니다. 2.405 ms 는 "편도 지연이 한쪽으로 완전히
쏠렸을 때"의 값이며, WiFi 상하향은 보통 비슷하므로 실제 오차는 이보다
훨씬 작을 가능성이 높습니다. **다만 그것을 증명할 방법이 이 측정 안에 없습니다.**

증명 가능한 방법은 검증방법 ① (ms 스톱워치를 두 폰으로 동시 촬영)이며,
폰 2대가 준비된 뒤에 수행합니다.

### 2.405 ms 가 결과에 주는 영향 (참고)

| 항목 | 값 |
| --- | --- |
| 60fps 프레임 간격 | 16.67 ms |
| 상한 2.405 ms 의 비중 | **14.4%** |
| 손목 5 m/s 일 때 위치 오차 (v·ε) | 약 12 mm |
| 데모에서 측정된 파이프라인 잡음 (평균 재투영) | 약 20 mm |
| 데모 IK 마커 RMS | 22.7 mm |

→ 지배적이지는 않지만 무시할 수준도 아닙니다. 목표를 낮추기 전에
경로 개선을 먼저 시도합니다.

### 원인 분리 — "바닥인가 표본 부족인가"

최소 RTT 숫자 하나로는 다음을 구분할 수 없습니다.

| 상황 | 대응 |
| --- | --- |
| 이미 물리적 바닥 | 코드로 불가. **경로**를 바꿔야 함 (유선 랜, 5GHz) |
| 표본 부족 / 꼬리가 두꺼움 | **왕복 횟수**를 늘리면 내려감 |

그래서 RTT 분포(p0 / p10 / p50 / p90 / 히스토그램)를 계산해 앱 화면과 로그에
노출하도록 했습니다 (`RttProfile`). `p50 / p0` 비율로 위 두 상황을 판정하고
다음 행동을 문장으로 출력합니다.

### 1차 실측에서 찾아낸 코드 결함 3건

| # | 결함 | 영향 | 조치 |
| --- | --- | --- | --- |
| ① | 왕복 간격 5 ms | iOS 가 매 왕복 사이 WiFi 무선을 절전시킴. 우리는 **최소** RTT 만 쓰므로 표본 다양성은 이득이 없고 손해만 있음 | 기본 간격 **0(연사)**. 워밍업 10회 추가 |
| ② | `phase` 를 매 왕복 갱신 | `@Published` 라 SwiftUI 가 매번 리렌더 → MainActor 점유 → 다음 왕복 t1 이 늦게 찍힘. **측정기가 측정값을 망침** | UI 갱신을 20회로 묶음 |
| ③ | `t1` 직후 `JSONEncoder` 실행 | 리플렉션 기반이라 수십~수백 µs. 전부 "t1 이후 ~ 패킷 출발 전"에 들어가 RTT 를 부풀림 | `time_req` 전용 문자열 조립 인코더. 바이트 동일성을 테스트로 못박음 |

추가로 `send` 를 `await` 하지 않고 `close()` 를 호출해
`POSIXErrorCode 89 (Operation canceled)` 가 났습니다. 데이터 손실은
없었지만(마스터가 `time_result` 수신 확인) 송신 완료를 기다리도록 고쳤습니다.

## 3.12 클럭 동기 — 2단계 종료 (2026-09-24)

### 측정 전체 기록 (아이폰 11 ↔ PC 마스터, 둘 다 공유기 WiFi)

| 시각 | 빌드 | 설정 | 최소 RTT | 중앙값 | 최대 | 오차 상한 |
| --- | --- | --- | --- | --- | --- | --- |
| 17:56 | 0.2.0 | 40회·간격5ms·워밍업X | 4.810 | — | — | 2.405 |
| 18:22 | 0.3.0/7 | 120회 연사+워밍업 | 4.435 | — | — | 2.218 |
| 18:58 | 0.3.0/7 | 동일 | 5.989 | — | — | 2.995 |
| 19:10 | 0.3.0/9 | 400회 분산 | 5.797 | 9.805 | 144.1 | 2.899 |
| 19:11 | 0.3.0/9 | 동일 | 4.383 | 8.825 | 131.8 | 2.191 |
| 20:04 | 0.3.0/10 | 400회 분산·표준 | **4.076** | 6.611 | 180.3 | **2.038** |
| 20:04 | 0.3.0/10 | 400회 분산·음성우선 | 4.661 | 9.262 | **24.5** | 2.331 |

### 결론 — 4.0 ms 가 이 경로의 바닥입니다

7회 측정 최소 RTT: 4.076 ~ 5.989 ms. **설정을 어떻게 바꿔도 4.0 ms 아래로
내려가지 않았습니다.** 최고 기록 4.076 ms → 오차 상한 **2.038 ms**.
목표 2.000 ms 대비 **초과분 0.038 ms (38 µs)**.

측정 간 편차(4.08~5.99 ms)가 남은 초과분의 50배입니다. 즉 **목표는 측정
정밀도 안에서 달성**되었고, 더 쥐어짜는 것은 의미가 없습니다.

### 실패로 기록하는 시도 2건

| 시도 | 의도 | 결과 |
| --- | --- | --- |
| 워밍업 + 연사(간격 0) | 무선 절전 회피로 최소 RTT 감소 | **효과 증명 못 함.** 18:22 에 4.435 가 나왔지만 18:58 에 5.989. 측정 간 편차가 주장한 개선폭보다 큼 |
| 버스트(시간 분산 표본화) | 측정 간 편차 감소 | **실패.** 19:10 5.797 / 19:11 4.383. 편차 그대로 |

### 절반만 맞은 가정 1건 — 통신 우선순위

최대 RTT 144~180 ms 는 공유기 비콘 주기(약 100 ms)를 기다린 흔적으로
보였습니다. 절전 중인 기기는 버퍼된 하향 데이터를 비콘까지 기다립니다.

음성 등급(AC_VO)으로 바꾼 결과:

- **최대 180.3 → 24.5 ms (7배 개선).** 절전 버퍼링 우회 **확인됨**.
- **최소 4.076 → 4.661 ms.** 개선 없음(편차 범위 내).

오차 상한은 최소 RTT 만으로 정해지므로 **목표 달성에는 기여하지 못했습니다.**
그래도 기본값으로 채택했습니다: 예약 시작 명령은 한 번만 보내므로
꼬리(최대값)가 곧 그 명령의 위험입니다. 180 ms 보다 24 ms 가 안전합니다.

### 구성 확정 — 폰은 항상 공유기 WiFi

아이폰이 공기계(셀룰러 없음)라 개인용 핫스팟을 켤 수 없습니다.
따라서 다음이 **확정**입니다.

| 구성 | 공중 건너기 | 가능 여부 |
| --- | --- | --- |
| 폰 ↔ 폰, 공유기 경유 | 4 | **이 구성으로 갑니다** |
| 폰 ↔ 폰, 마스터폰 핫스팟 | 2 | 불가 (공기계) |
| 폰 ↔ PC(WiFi) | 4 | 지금 측정 구성 = 실제와 동일 |
| 폰 ↔ PC(유선) | 2 | 측정용으로만 의미. 미시도 |

폰↔폰도 공중 4번이므로 **지금 측정한 값이 실제 시스템의 값입니다.**
경로를 줄일 수단이 없습니다.

### ★ 부수 발견 — 절전 중 시계가 멈춥니다 (설계 가정 확인)

| 항목 | 값 |
| --- | --- |
| 19:11 오프셋 | +5,522,186 ms |
| 20:04 오프셋 | +7,560,244 ms |
| 오프셋 증가 | 2,038,058 ms = **34분** |
| 실제 경과 시간 | 52분 38초 |
| 폰 시계가 진행한 시간 | 18분 40초 |

`CLOCK_UPTIME_RAW` 가 절전 중 **멈춘다는 것이 실측으로 확인**됐습니다
(규약 §1 의 가정). 책상에 놓인 52분 중 34분을 폰이 잤습니다.

**따라서 오프셋은 촬영 직전에 매번 다시 측정해야 합니다.** 미리 재둔 값은
폰이 한 번이라도 자면 무효입니다. 현재 설계(동기 → 예약 시작)가 이미
그 순서이므로 변경 불필요. 촬영 중에는 `isIdleTimerDisabled = true` 로
화면을 켜 두어 절전을 막습니다.

### 오차 상한 2.038 ms 의 실제 영향

| 기준 | 값 |
| --- | --- |
| 60fps 프레임 간격 | 16.67 ms |
| 2.038 ms 의 비중 | **12.2%** (약 1/8 프레임) |
| 걷기(대부분 관절 2 m/s) 위치 오차 | 약 **4 mm** |
| 빠른 팔 동작(손목 5 m/s) | 약 **10 mm** |
| 데모 실측 파이프라인 잡음 (평균 재투영) | 약 20 mm |
| 데모 IK 마커 RMS | 22.7 mm |

걷기·일반 동작에서는 파이프라인 잡음의 1/5 수준으로 **무해**합니다.
빠른 팔 동작에서 약 10 mm 로 잡음과 비슷한 수준이 됩니다.

### 보험 — 영상 기반 정렬이 2차 채널로 남아 있습니다

Pose2Sim 의 `synchronization()` 은 카메라 간 움직임 상관으로 시간차를
찾습니다. 우리는 타임스탬프가 더 정확하므로 건너뛸 계획이었지만,
**클럭 오차가 반 프레임(8.33 ms) 안에 있으면 이 기능으로 검증·보정이
가능합니다.** 2.038 ms 는 그 안에 넉넉히 들어옵니다.

즉 클럭 동기는 "완벽해야 하는 단일 실패점"이 아니라 "충분히 가까우면
되는 1차 정렬"입니다. 이 판단으로 2단계를 닫습니다.

### 남은 미검증 항목 (3단계 이후로 이관)

| 항목 | 이유 |
| --- | --- |
| 폰↔폰 실측 | 2번째 아이폰 미확보 |
| 검증방법 ① ms 스톱워치 | 폰 2대 필요. **오차의 유일한 직접 측정법** |
| 유선 PC 로 공중 2번 측정 | 실제 구성이 아니라 참고용. 우선순위 낮음 |
| UDP 전환 | 최소 RTT 가 바닥이라 이득 불확실. 규약 §2 에 기준만 기록 |

카메라 4대 × 2분이면 CPU 약 3시간 → GPU 약 15분(영상 없이)입니다.

### 정확도 — CPU 와 GPU 결과 비교 (`tools/pose_compare.py`)

- 검출 일치: 749프레임 중 748프레임 양쪽 모두 검출 (1프레임만 CPU 단독)
- 관절 위치 차이: **중앙값 0.022 px**, 95% 3.2 px
- 프레임의 77% 는 사실상 동일(중앙값 0.1 px 미만)
- 큰 차이(60~259 px)는 전부 **발가락**이고 신뢰도가 양쪽 모두 0.3 안팎으로 같았습니다.
  신뢰도가 경계에 걸린 관절에서 두 연산 경로가 서로 다른 후보를 고른 것입니다.
  어느 쪽이 맞다고 할 근거가 없으며, 저신뢰 관절은 Pose2Sim 의 필터와
  삼각측량 이상치 제거가 걸러냅니다.

→ 1080p 에서 1 px ≈ 2 mm 이고 데모 파이프라인 잡음이 약 20 mm(≈10 px)이므로
**GPU 로 바꿔도 정확도 손실은 없습니다.**

### 설치 조합 (재현용: `tools/setup_pose2sim_gpu.ps1`)

| 패키지 | 버전 | 이유 |
| --- | --- | --- |
| onnxruntime-gpu | 1.22.0 | 1.30 은 CUDA 13 요구 — 드라이버 566.14 는 CUDA 12 까지 |
| nvidia-cudnn-cu12 | 9.8.0.87 | 9.26 은 ORT 1.22 와 안 맞아 실행 중 CPU 로 조용히 후퇴 |
| nvidia-cuda-runtime/cublas/cufft/curand-cu12 | 12.9 계열 | pip 로 받아 시스템 CUDA 설치 없이 동작 |

드라이버를 올리지 않고 pip 패키지만으로 해결했습니다. 시스템 변경 0.

### ★ 함정 4가지

1. **`get_available_providers()` 에 CUDA 가 보여도 GPU 로 돈다는 보장이 없습니다.**
   DLL 누락, cuDNN 불일치 모두 경고만 찍고 CPU 로 되돌아가 결과는 정상으로 나옵니다.
   `tools/ort_gpu_check.py` 로 제공자를 하나만 지정해 실제 추론 속도를 재야 합니다.
2. **Config.toml 에서 `device` 만 지정하면 무시됩니다.** Pose2Sim 이
   "Backend is set to 'auto' but device is not" 를 찍고 자동 판정(→ CPU)으로 갑니다.
   `backend = 'onnxruntime'` 과 `device = 'CUDA'` 를 **함께** 줘야 합니다.
   자동 판정은 `torch.cuda.is_available()` 까지 요구하는데 torch 가 없으므로
   자동으로는 절대 GPU 가 선택되지 않습니다.
3. **Pose2Sim 을 부르기 전에 `onnxruntime.preload_dlls()`** 를 호출해야
   pip 로 받은 CUDA DLL 을 찾습니다.
4. (측정) **게임 등 다른 GPU 작업이 돌고 있으면 GPU 가 CPU 보다 느려질 수 있습니다.**
   2026-09-25 게임 중 측정에서 7분 08초가 나와 CPU 보다 느렸습니다. 측정 전
   `nvidia-smi` 로 유휴 상태를 확인합니다.

## 4.2 키포인트 리샘플러 (`server/mocapsync/resample.py`, 2026-09-27)

### 하는 일

카메라마다 프레임 찍는 순간이 다릅니다(최대 반 프레임 = 8.3 ms). 사이드카의 프레임 시각을
공통 시계로 바꾸고, 관절 좌표를 시간의 함수로 이어 **모든 카메라가 같은 60Hz 격자 시각**
에서 값을 갖게 합니다. 결과는 `pose-sync/` 에 써서 Pose2Sim `synchronization()` 을 건너뜁니다.
실행: `tools/resample_poses.py <프로젝트> --map cam01=<사이드카> --map cam02=<...>`

### 지키는 규칙

| 규칙 | 값 | 이유 |
| --- | --- | --- |
| 외삽 없음 | 모든 카메라가 동시에 찍은 구간만 격자 | 관측 밖 값은 지어낸 값 |
| 긴 공백은 잇지 않음 | 50 ms 초과 | 가려진 구간을 곡선으로 지어내지 않음 |
| 튀는 곳에서 끊음 | 인접 관측 간 200 px 초과 | 추적기가 슬롯을 다른 사람에게 넘긴 흔적 |
| 저신뢰 점 제외 | 신뢰도 0.3 미만 | Pose2Sim 삼각측량 기본 임계값과 같음 |
| 프레임 수 불일치는 오류 | JSON > 사이드카 이면 중단 | 조용히 모든 시각이 밀리는 것을 막음 |
| 신뢰도는 직선 보간 | — | 곡선은 1 초과·음수가 나올 수 있음 |

### 보간법 — makima (hold-out 실측, `tools/resample_holdout.py`)

실제 아이폰 영상(1086프레임)에서 짝수 프레임만 입력으로 주고 홀수 프레임 시각을 맞추게
했습니다. 입력 간격 33 ms 로 실사용(16.7 ms)보다 어려운 조건입니다. 정답(홀수 프레임)에도
검출 잡음이 있어 오차가 0 이 될 수 없으므로 **방법끼리의 상대 비교**가 핵심입니다.
슬롯별 리샘플러 기준, 비교 8,993점, 평균 오차(px):

| 방법 | 전체 평균 | 중앙값 | 손목 L/R | 팔꿈치 L/R | 발목 L/R |
| --- | --- | --- | --- | --- | --- |
| nearest (보간 없음) | 9.30 | 6.54 | 14.38 / 14.63 | 11.00 / 11.22 | 6.97 / 6.88 |
| linear | **4.71** | 3.12 | 3.43 / 3.74 | 3.61 / 3.44 | 3.35 / 3.10 |
| cubic | 4.97 | 3.18 | 3.07 / 3.41 | 3.54 / 3.25 | 3.56 / 3.32 |
| pchip | 4.76 | 3.10 | 3.05 / 3.37 | 3.53 / 3.24 | 3.40 / 3.10 |
| makima | 4.72 | **3.06** | **3.01 / 3.31** | **3.48 / 3.16** | 3.39 / 3.10 |

- cubic spline 은 검출이 튀는 곳에서 출렁여(overshoot) 곡선 계열 중 가장 나쁩니다.
- makima 는 전체 평균이 linear 와 0.01 px 차이(사실상 같음)이고, 빠른 관절
  (손목·팔꿈치)과 중앙값에서 가장 좋습니다. 매끈한 합성 움직임에서는 곡선 계열이
  linear 보다 훨씬 정확합니다(`server/tests/test_resample.py`). 두 조건 모두 좋은 makima 로 정했습니다.

### 버그 1건 — 사람을 고르다가 엉뚱한 사람을 골랐음

처음 구현은 프레임마다 "관절이 가장 많은 한 명"만 골라 이었습니다. 공식 데모
cam01/cam02 에는 **두 사람**이 찍혀 있어 cam02 에서 다른 사람을 골랐고,
Pose2Sim 이 `Camera cam02 was excluded 100% of the time` 으로 cam02 를 통째로 버렸습니다.
고른 사람이 프레임마다 바뀌면 두 사람의 궤적을 섞어 잇는 문제도 있었습니다.

→ **사람을 고르지 않고 추적기 슬롯(사람 번호)별로 따로 잇습니다.** 누가 피험자인지는
Pose2Sim `personAssociation()` 이 여러 카메라를 보고 정합니다.

### 공식 데모로 배관 검증 (`tools/demo_resample_check.py`)

리샘플러 → personAssociation → triangulation → filtering 을 돌렸습니다.

원본과 같습니다. 오프셋이 정수 프레임이라 이 시험은 **보간이 아니라 배관**(pose-sync 를

### 한계 — 아직 재지 못한 것

- **서브프레임 이득 자체는 측정되지 않았습니다.** 데모 영상에는 프레임 시각이 없고,

## 4.3 파이프라인 러너 (`tools/run_session.py`, `server/mocapsync/pipeline.py`, 2026-09-27)

```powershell
& "$env:USERPROFILE\.venv\pose2sim_gpu\Scripts\python.exe" tools\run_session.py <세션 이름 또는 폴더>
```

입력 찾기 → 검사 → 프로젝트 만들기 → 2D(GPU) → 리샘플 → personAssociation →
triangulation → filtering → 요약. 결과는 `~/Pose2SimWork/sessions/<세션>/`,
실행 기록은 `mocapsync_run.json` 과 `logs/run_session_*.log`.
종료 코드 0 = 3D 완료, 10 = 3D 전까지(캘리브레이션 없음·1대), 2 = 입력 문제, 3 = 단계 실패.

### 리그 = 캘리브레이션 + "어느 폰이 cam01 인가"

`~/Pose2SimWork/rig/` 에 Pose2Sim 형식 `Calib.toml` 한 개와 `cameras.json`
(`{"cam01": "<기기ID>", ...}`)을 둡니다. 폰을 옮기면 새 리그입니다.
**Pose2Sim 은 캘리브레이션 카메라와 영상을 이름이 아니라 순서로 짝짓습니다**
(`triangulation.py`: `computeP(calib)` 순서 ↔ pose 폴더를 끝 숫자로 정렬한 순서).
그래서 러너가 기기 ID 로 camNN 을 정하고, 캘리브레이션 파일 안 순서가 cam01, cam02 …
인지, 해상도가 영상과 맞는지(±2%, 공식 데모도 1080 대 1088) 확인합니다.

### 멈추는 조건 (조용히 틀린 결과 대신)

영상·사이드카 짝 불일치, 덜 올라온 `.part`, 사이드카/세션 검증의 치명 항목,
리그에 없는 폰 · 리그에는 있는데 이번에 없는 폰, 캘리브레이션 순서·해상도 불일치,
한글 경로(OpenSim), 작업 폴더 부모의 `Config.toml`(Pose2Sim 배치 모드로 설정이 섞임).

### 실측 검증 — 공식 데모를 "폰 업로드"처럼 꾸며서 (`tools/make_demo_session.py`)

기기 ID 를 cam 순서와 반대로 붙여, 리그 표를 무시하면 드러나게 했습니다.

| --- | --- | --- | --- |

### 이 시험으로 찾은 것 2건

1. **버그 — 옛 2D 결과를 다른 영상에 재사용.** 리그 표를 바꿔 다시 돌렸더니 cam01 폴더에
   옛 cam01 영상의 2D 가 남아 새 사이드카 시각과 섞인 채 오류 없이 3D 까지 나왔습니다.
   → camNN 마다 원본 영상(기기·경로·크기·수정시각)을 `pose_sources.json` 에 적고,
   하나라도 바뀌면 `pose/` 를 통째로 지웁니다. 일부만 지우면 안 됩니다 — Pose2Sim 은
   pose/ 의 첫 폴더만 보고 추정 전체를 건너뜁니다.
2. **재투영 오차만 보면 속습니다.** 카메라를 뒤바꾸자 오차가 6.0 px 로 오히려 좋아졌습니다.
   Pose2Sim 이 허용치(15 px) 밑으로 내려갈 때까지 맞지 않는 카메라를 빼고 계산하기
   때문입니다. → 배제 비율이 50% 이상인 카메라가 있으면 재투영 오차를 "좋음"으로
   판정하지 않고 경고합니다. 카메라 2대는 뺄 카메라가 없어 오차가 작게 나오는 편이라
   (같은 영상 2대 8.6 / 4대 10.6 px) 따로 참고 문구를 붙입니다.

### 남은 것

- 폰 2대 실촬영과 캘리브레이션(리그 만들기)은 아직입니다. 리그를 만드는 도구는 캘리브레이션 단계에서 만듭니다.
- ★ **카메라 2대에서는 뒤바뀜이 품질 지표에 전혀 안 나타납니다.** 실측: 뒤바꾼 2대는
  재투영 8.2 px·배제 0%·빈 좌표 0%로 올바른 2대(8.6 px)와 구별이 안 되는데, 3D 는
  4대 결과와 중앙값 545 mm(90% 1.6 m) 떨어진 쓰레기였습니다. 두 광선은 캘리브레이션이
  틀려도 거의 늘 가까이 지나가기 때문입니다. 폰 2대 구성에서는 **리그 표(cameras.json)가
  유일한 방어선**이고, 그래서 캘리브레이션 도구가 이 표를 직접 써야 합니다(사람이 손으로
  쓰지 않게).
- 올바른 2대(데모 cam01 + cam03)도 4대 결과와 중앙값 61 mm(90% 212 mm) 차이가 났고
  왼쪽 종아리 길이 SD 가 72.5 mm 였습니다. 이 두 카메라 조합의 한계인지 2대 구성 일반의
  한계인지는 이 시험으로 가를 수 없습니다. 아이폰 2대 실촬영에서 다시 봐야 합니다.

## 4.5 캘리브레이션 도구 (`tools/calibrate.py`, `server/mocapsync/calib.py`, 2026-09-28)

촬영 가이드는 `docs/CALIBRATION.md`. 여기는 왜 이렇게 만들었나입니다.

```powershell
& "$env:USERPROFILE\.venv\pose2sim_gpu\Scripts\python.exe" tools\calibrate.py intrinsics <세션>   # 폰마다 한 번
& "$env:USERPROFILE\.venv\pose2sim_gpu\Scripts\python.exe" tools\calibrate.py extrinsics <세션>   # 폰을 놓을 때마다
& "$env:USERPROFILE\.venv\pose2sim_gpu\Scripts\python.exe" tools\calibrate.py status
```

| 단계 | 방법 | 결과 |
| --- | --- | --- |
| 내부 (렌즈 특성) | 판을 손에 들고 촬영 → 느린 장면만 → 서로 다른 장면 최대 60개(farthest point) → `calibrateCamera` (k1 k2 p1 p2 k3) → 오차 큰 장면 빼고 한 번 더 → 안 쓴 장면으로 검산 | `~/Pose2SimWork/intrinsics/<기기ID>.json` |
| 외부 (위치·방향) | 폰 전부 동시 녹화, 판을 두 폰이 함께 보게 → 공통 격자(8 Hz)의 각 시각에 앞뒤 프레임 꼭짓점을 **시각대로 보간** → PnP 로 초기값 → 카메라 자세 + 장면마다 판 자세 **번들 조정**(soft L1) → 튀는 관측 빼고 한 번 더 | 기준 카메라 좌표의 카메라 자세 |
| 바닥 | 마지막에 바닥에 눕힌 판: 1.5초 이상 멈춤 + 판 위쪽이 카메라 위쪽과 60도 안 → 멈춘 동안 꼭짓점 평균으로 자세 한 번 | 월드: Z 위, 바닥 0, 원점 = 판 가운데, Y = cam01 이 보는 수평 방향 |
| 리그 | `Calib.toml`(Pose2Sim 형식, cam01, cam02 … 순서) + **`cameras.json`(사이드카 deviceId 로 자동)** + `rig_report.json` + `check_camNN.jpg` | `~/Pose2SimWork/rig/`, 이전 것은 `rig_backup/<시각>/` |

### 왜 Pose2Sim calibration() 이 아닌가

- 외부 방식이 'board'(바닥 판 한 장을 모든 카메라가) / 'scene'(줄자로 잰 점을 손으로 클릭) 뿐입니다.
  'keypoints' 는 설정 목록에만 있고 0.10.49 코드에서 `NotImplementedError` 입니다 (calibration.py:963).
- A4 판(23 mm)을 초광각(f ≈ 700 px)으로 3 m 에서 보면 한 칸 약 5 px — 바닥 판 하나로 모든
  카메라를 맞추기엔 작습니다. 동기 촬영이면 판을 **카메라 가까이** 들어 크게 보일 수 있습니다.
- 카메라 순서를 사람이 정하지 않게 하려면 도구가 deviceId 를 알아야 합니다 (§4.3 "남은 것").

### 조용히 틀리는 곳을 막은 것

1. **판 방향.** `findChessboardCorners` 는 어느 모서리부터 세는지 보장하지 않습니다. 카메라마다 다르게
   세면 스테레오가 틀린 채 "성공" 합니다. (1) 격자 손잡이 방향(첫 줄 × 첫 열 > 0), (2) 안쪽 칸 전체의
   색(첫 칸 검정)으로 순서를 하나로 정합니다. 7×10 칸 판은 180도 돌리면 색이 뒤집혀 구분됩니다.
   시험: 판을 0/90/180/270/33/212도 돌려도 꼭짓점 번호가 같은 모서리 (`test_calib.py`).
2. **같은 순간.** 두 폰은 찍는 순간이 최대 반 프레임 다릅니다. 가장 가까운 프레임끼리 짝지으면
   판이 0.3 m/s 일 때 2.5 mm 어긋난 채로 풉니다. 앞뒤 프레임 사이를 시각대로 보간하고, 프레임이
   빠진 곳(간격 1.6배 이상)은 잇지 않습니다.
3. **롤링셔터·흔들림.** 앞뒤 프레임의 꼭짓점 이동으로 속도를 재서 빠른 장면을 버립니다
   (내부 60 px/초 = 60fps 에서 프레임당 1 px, 외부 120 px/초). 그래서 가이드가 "자세마다 1초 멈춤".
4. **축척·방향 검산.** 판 자세와 무관하게 카메라 자세만으로 꼭짓점을 삼각측량해 한 칸 길이를 잽니다
   (23 mm 가 나와야 함). 판정이 나쁘면 리그를 쓰지 않습니다 (`--force` 로만).
5. **Pose2Sim 규칙.** rotation = Rodrigues(월드→카메라), translation = 미터, 카메라는 파일 순서로 짝지음.
   시험에서 Pose2Sim 과 같은 식(`computeP`, undistort 경로의 `getOptimalNewCameraMatrix`)으로
   투영해 우리 모델과 같은 픽셀인지 확인합니다. 러너의 `load_rig`/`check_calibration` 도 통과.

| 처음부터 끝까지 (.mp4 + 사이드카, 1280x720, 폰 시계 3000초 차이 + 7 ms 어긋남) | 렌즈 오차 0.14/0.19 px, 리그 재투영 0.3 px, 한 칸 40.00 mm(+0.01%), 높이 1.00/1.20 m, 러너가 리그를 받아들임 |

실폰(아이폰 1080p .mov)으로는 판 없는 영상에서 "판이 한 번도 보이지 않았습니다" 까지만 확인했습니다.
**실제 판 촬영으로는 아직 검증 전입니다.**

### 찾은 것 — Pose2Sim 의 왜곡 펴기는 강한 왜곡에서 덜 폅니다

Pose2Sim(`undistort_points=true`)은 `cv2.undistortPoints` 를 반복 횟수 지정 없이 부릅니다. OpenCV
기본(5회)은 강한 통 왜곡(k1 = -0.25, 가로 104도)의 화면 구석에서 **최대 17 px** 덜 폅니다
(타원 r<1 안에서는 0.7 px, 가운데 절반은 0). 왜곡이 약하면(k1 = -0.12) 0.001 px 로 무시할 만합니다.
도구가 렌즈 특성마다 이 값을 재서(`pose2simUndistortErrorPx`) 1 px 를 넘으면 알립니다.
아이폰 초광각의 실제 왜곡(기하 왜곡 보정이 켜져 있는지)은 렌즈 특성 촬영 뒤에 알 수 있습니다.
크게 나오면 러너에서 `cv2.undistortPoints` 반복 횟수를 늘리는 방법이 있습니다.

### 한계 — 아직 모르는 것

- **바닥 판이 초광각에서 잡히는지.** 폰이 수평이면 바닥은 약 1.3 m 앞부터 보이고, 거기 누운 A4 판은
  한 칸이 약 10×6 px 입니다(찾을 수 있는 하한 근처). 가이드는 "폰을 10도 숙이고 1~1.5 m 앞" 입니다.
  못 찾으면 리그는 쓰되 위쪽 방향을 카메라 기울기로 어림하고 경고합니다. 대안: 바닥용 큰 판,
  또는 앱이 가속도계의 중력 방향을 사이드카에 기록 (앱 빌드 필요).
- 기준값(0.5 px, 1.0 px, 1%)은 문헌·경험값입니다. 실폰 결과를 보고 조정합니다.

## 5. 촬영 규칙 (정확도의 80%를 결정)

- **60fps 이상 필수** (Pose2Sim 공식: 60Hz 미만은 정확도 하락)
- 카메라 **4대 실용 하한**, 공식 권장 6대
- 2대일 때 최적 배치: 정면 1대 + 측면 45° 1대, 둘 다 **골반 높이**
- 피험자 **바로 위 탑뷰는 금지** (결과 나쁨)
- 1080p 충분. `crf 30` 압축은 정확도 영향 거의 없이 용량 1/10
- **몸에 붙는 옷** (헐렁하면 오차 10cm 이상)
- 촬영 **5초 이상 ~ 몇 분 이내** (그 이상은 폰 클럭 드리프트)

## 6. 검증 방법 (반드시 실행)

1. **ms 스톱워치를 전 카메라로 촬영** → 실제 동기 오차 측정 (가장 정량적)

4. **카메라 leave-one-out** 비교
5. **Pose2Sim `logs.txt`**: 재투영 오차, 카메라별 배제 비율

## 7. 작업 순서

0. (사람이 함) PC에서 Pose2Sim 데모 실행 → `.trc` 생성 확인
1. GitHub 리포 + GitHub Actions APK 빌드 워크플로

   - **성공 판정: 폰 2대 클럭 오차 2ms 미만**
   - 이 단계가 프로젝트의 사활을 결정합니다. 여기서 실패하면 위에 뭘 쌓아도 의미가
     없으므로, 일부러 녹화도 없는 최소 앱으로 잘랐습니다. 숫자 하나로 성공/실패를
     판정할 수 있게요.
3. 녹화 + 예약 시작 + 타임스탬프 사이드카 + 기기 진단 화면
4. PC 업로드 수신 + 키포인트 리샘플러 + Pose2Sim 자동 실행
5. 웹 3D 뷰어 + 품질 대시보드
6. 마스터 미리보기 그리드, 배터리/온도 모니터
